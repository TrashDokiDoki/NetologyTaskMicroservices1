**security**

**POST /v1/register**

**POST /v1/token**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/token.

**GET /v1/user**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.

**POST /v1/upload**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.

# Решение

## Задача 1. API Gateway

Для организации единой точки входа в микросервисную систему сравним Nginx, Traefik и Kong Gateway.

| Критерий | Nginx (Open Source) | Traefik Proxy | Kong Gateway (Open Source) |
|---|---|---|---|
| Маршрутизация по конфигурации | Да: `location`, `proxy_pass`, upstream | Да: HTTP-роутеры и сервисы, динамическая конфигурация | Да: Routes и Services, в том числе декларативная конфигурация |
| Проверка аутентификации | Да: базовая аутентификация, `auth_request` к внешнему сервису; JWT обычно требует внешнего решения | Да: BasicAuth и ForwardAuth к внешнему сервису | Да: плагины Key Authentication, JWT и Basic Authentication |
| Терминация HTTPS | Да | Да | Да |
| Балансировка запросов | Да | Да | Да |
| Интеграция с контейнерами | Возможна, конфигурация преимущественно вручную | Удобное обнаружение сервисов Docker/Kubernetes | Docker/Kubernetes, конфигурация через API или декларативно |
| Эксплуатация | Простое и популярное решение, но функции API Gateway собираются из модулей и конфигурации | Удобен при динамическом составе сервисов | Специализированный API Gateway с готовыми плагинами, но дополнительными компонентами и настройками |

**Выбор: Kong Gateway (Open Source).**

Kong удовлетворяет всем трём требованиям: по правилам Routes направляет запросы к соответствующим Services, проверяет аутентификационные данные с помощью плагинов, принимает HTTPS-соединения и передаёт запросы внутренним сервисам. Кроме того, Kong поддерживает ограничение частоты запросов, журналирование и другие API-функции. Это позволяет управлять общей политикой доступа на шлюзе, а не реализовывать её отдельно в каждом микросервисе.

Для компании с большим количеством микросервисов централизованная настройка API удобнее, чем поддержка самодельного набора правил Nginx. Компромисс — Kong сложнее в администрировании, чем базовый Nginx, а часть продвинутых функций доступна только в платных редакциях. Если же главная задача — интеграция с Kubernetes без сложной политики API, разумной альтернативой будет Traefik.

## Задача 2. Брокер сообщений

Сравним RabbitMQ, Apache Kafka и NATS с JetStream. Для корректного сравнения учитываем, что надёжное хранение и отказоустойчивость зависят от настроек конкретного брокера.

| Критерий | RabbitMQ | Apache Kafka | NATS + JetStream |
|---|---|---|---|
| Кластеризация и отказоустойчивость | Да, кластер и реплицируемые quorum queues | Да, кластер брокеров с репликацией партиций | Да, кластер JetStream с репликацией |
| Хранение сообщений на диске | Да, quorum queues постоянно сохраняют сообщения | Да, сообщения хранятся в журнале на диске | Да, при настройке file storage в JetStream |
| Скорость работы | Высокая для очередей задач и обмена событиями | Очень высокая пропускная способность на больших потоках данных | Высокая производительность и низкая задержка |
| Форматы сообщений | Передаёт произвольные данные, включая JSON, XML, Protobuf и бинарные сообщения | Передаёт произвольные байты; можно применять JSON, Avro, Protobuf и др. | Передаёт произвольные байты; возможны JSON, Protobuf и др. |
| Разграничение доступа | Пользователи, virtual hosts, права на ресурсы | ACL для топиков и групп потребителей | Accounts, users, разрешения на subjects |
| Простота эксплуатации | Есть веб-интерфейс управления, документация, много готовых клиентов | Относительно сложная эксплуатация и настройка | Компактный сервер, но надёжный JetStream-кластер требует настройки и мониторинга |
| Наиболее подходящие задачи | Очереди задач, команды, асинхронное взаимодействие сервисов | Большие потоки событий, аналитика, длительное хранение и повторное чтение | Быстрый обмен сообщениями и лёгкая событийная инфраструктура |

**Выбор: RabbitMQ с quorum queues.**

RabbitMQ подходит для типичной корпоративной микросервисной системы, в которой требуется надёжная асинхронная обработка заказов, уведомлений и фоновых задач. Он поддерживает маршрутизацию сообщений с помощью exchanges, подтверждения публикации и обработки, а также разграничение прав доступа к очередям и другим ресурсам.

Для высокой доступности предлагается кластер из **трёх узлов RabbitMQ** с quorum queues и репликацией между узлами. Очереди должны быть объявлены как долговременные; следует использовать publisher confirms, ручные подтверждения потребителей и обработку повторной доставки. Это снижает риск потери сообщений при отказах, хотя приложения всё равно должны корректно обрабатывать дубликаты.

По сравнению с Kafka, RabbitMQ обычно проще внедрять для традиционных очередей задач и маршрутизации сообщений. Kafka предпочтительнее, если основной приоритет — обработка очень больших потоков событий с длительным хранением и многократным чтением. NATS JetStream может оказаться удобнее при приоритете минимальных задержек и лёгкости инфраструктуры.

**Итог:** для рассматриваемой компании предлагаются Kong Gateway в качестве единой точки входа и RabbitMQ в качестве брокера сообщений. Окончательный выбор для production следует подтвердить нагрузочными испытаниями и проверкой отказоустойчивости на реальных сценариях.
